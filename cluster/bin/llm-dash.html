From llama-server's logs and its /slots: each console keeps its last 200 requests while llm-dash runs, and reads back the current server run's when it starts. "Reused" is prompt that was already in the cache; "New" had to be read. The layer map is worked out from the model file and the run script the way llama.cpp's loader assigns layers (RPC devices first, -ts split points, the input embedding in RAM); it shows weights only, not the KV cache.

Model sync

Model sync and the RPC weight cache can't both be on. With model sync on, /root/models is kept identical on both consoles, and turning it on deletes the worker's RPC weight cache to make room. Every pool start then sends the worker's share (~6 GB) over the link again, which takes longer. Inference is the same. Turning it off deletes nothing; the cache rebuilds on the next pool starts.

Each console keeps 6 h of samples (every 5 s) in memory; a restart of llm-dash clears them. The temperature is the chip's CPU-side sensor: Linux sees no GPU temperature and no fan speed. Buttons need the gateway's master key and act on the console they're under.
